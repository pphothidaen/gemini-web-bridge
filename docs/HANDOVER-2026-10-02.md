## 2. The central finding — KAN-236 measurement

**The browser sends 20 top-level fields; the worker's builder emits 10.**

The notebook binding is a branch at **`[0][3]`**, present **if and only if a
notebook chip is attached**. Inside it, `[0][3][0][2]` is an 88-character token:
charset `lower+upper+digit`, fingerprint `cff9779e`, **stable across turns and
across two different conversations** for the same notebook.

Cross-validated against **all seven** sanitized captures in the repo — the two
KAN-195 samples from 2026-09-29 in `docs/payload-samples/`, plus the five from
2026-10-02. Seven for seven:

| capture | chip | response cited | `[0][3]` |
|---|---|---|---|
| 09-29 A | yes | yes | present |
| 09-29 B | **yes** | **no** | present |
| 10-02 chip-present ×2 | yes | yes | present |
| 10-02 chip-repeat | yes | yes | present |
| 10-02 chip-absent | **no** | — | absent |
| 10-01 ungrounded | **no** | — | absent |

**Consequence:** a direct worker → `StreamGenerate` path can emit the 20-field
payload for a **known** notebook. It cannot derive a token for an **unknown** one.
Practical shape: DOM path on first contact, direct path thereafter.

**Not established:** whether the 88-char token differs for a *different* notebook.
Only one notebook has ever been observed, so "stable per notebook" is an
inference, not a measurement. **This is the single highest-value open question in
KAN-236** and it needs one capture against a second notebook.

## 3. Infrastructure built to get there

- `POST /debug/payload-capture` — arms/disarms the sanitized relay. **Authenticated,
  and deliberately NOT on `/health`**: `/health` answers 200 unauthenticated, so
  conversation metadata does not belong there.
- Every capture carries `extensionVersion` from `chrome.runtime.getManifest()` —
  the *loaded* build, so a capture can never be ambiguous about which classifier
  produced it.
- Per-string coarse descriptor (`fingerprint`, `charset`, `contains.notebook_id`)
  so a field can be **identified without being read**. Opt-in, gated on the arm,
  so the normal sanitized shape stays `{type, length, cls}`.
- `collection.last_progress_at` on `/health` — makes the heartbeat observable
  without a browser console.

## 5. Gotchas that cost real time here

- **Extension changes need a manual Reload** at `chrome://extensions`, in the
  *original* Chrome. Browser MCP is a different Chrome instance with zero
  extensions; Kapture blocks `chrome://` (`NAVIGATION_BLOCKED`) and its
  `new_tab` ignores the URL entirely.
- **After every version bump, re-run `scripts/build-extension.py`.** Skipping it
  at 4.7.30/4.7.31 left `dist/extension` two versions stale, and `dist/` is
  gitignored so nothing noticed. `--verify` catches it.
- **Navigate before arming, never after** — page-side capture state resets on
  navigation. Documented, then missed.
- **Hidden tabs get timer-throttled**, which silently starves the heartbeat.
  `kapture__show` before driving.
- `horo_consult` consumes the notebook attachment **per message**; a second
  grounded turn in the same conversation fails `no_citations_in_response`.
- `date +%s%3N` is GNU-only and silently emits `N` on macOS — use python.
- MCP is on **prod**, not the retired `pansakorn-pho` host. Both report
  `app:*` scopes, so the scopes alone prove nothing; check the reported version.

## 6. Two lessons worth inheriting

**Blind instruments.** Four appeared, each producing an **absence** in the same
confident register as a real result: a detached console reader, a relay wired in
one direction, a classifier blind to `notebooks://`, and a capture with no
provenance. None announced itself. What worked: make the instrument
self-identify, and ask what it *would* say if it were working before believing
an absence.

**Older captures are a research channel.** `docs/payload-samples/` held a
grounded/ungrounded pair since 2026-09-29 that nobody had compared against the
new data. It should have been the first thing consulted, not the last — and it
needs no browser. A corollary from the same day: I then retracted a *correct*
conclusion because I read "ungrounded" as "no chip attached", when "ungrounded"
describes the response and chip attachment describes the request. A retraction
should establish what a contradicting datum *means* before overturning anything,
not merely that it contradicts.
