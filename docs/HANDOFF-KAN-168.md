# HANDOFF — DO alarm never fires (KAN-168)

Written 2026-09-27, immediately after the instrumentation run.

**Read this first.** Everything below is measured, not inferred, except where a
line says *unproven*. The previous session's core mistake was repeatedly
concluding a root cause from circumstantial evidence and acting on it. This
document separates the two categories deliberately so the next session does not
repeat that.

## The bug

The Durable Object's alarm never fires. Consequently three things silently do
not run on production:

- the keepalive PING is never sent to the extension
- the stale-socket sweep never runs
- the MCP SSE `: keepalive` comment is never written

Symptoms measured on 2026-09-27:

- a connection sat at `idle=209s` against a 180s stale threshold and was never
  reaped
- `idle` climbed 234 → 248 → … → 423s monotonically, never resetting
- an MCP SSE stream ran 231s and received zero keepalives

## Root cause (FOUND — supersedes everything below)

**`ctx.alarm` is not a real property. The alarm was never armed.**

`scheduleAlarm()` contained:

```js
this.ctx.alarm = Math.max(1, Math.round(ms / 1000));
```

`DurableObjectState` has no `alarm` member. The full interface, from the
`worker-configuration.d.ts` generated by the pinned wrangler (4.133.0):

```
waitUntil, exports, props, id, storage, container?, facets,
blockConcurrencyWhile, acceptWebSocket, getWebSockets,
setWebSocketAutoResponse, getWebSocketAutoResponse,
getWebSocketAutoResponseTimestamp, setHibernatableWebSocketEventTimeout,
getHibernatableWebSocketEventTimeout, getTags, abort
```

No `alarm`. Assigning to it creates an ordinary own-property on the ctx object,
which the runtime never reads. **No alarm was ever scheduled, so `alarm()` could
never be called.** That is the whole bug, and it explains all four symptoms:
no keepalive PING, no stale sweep, no MCP keepalive.

Two compounding mistakes:

1. **Wrong API.** The real one is `ctx.storage.setAlarm(scheduledTime)`.
2. **Wrong units, even if the property existed.** `setAlarm` takes an
   **absolute** time (epoch ms or a `Date`), not a delay in seconds. A bare
   `120` is 1970-01-01T00:02:00Z — in the past, so it could never produce a
   future wakeup. The correct call is `setAlarm(Date.now() + ms)`.

### The proof (run locally, in `wrangler dev`)

A throwaway DO armed the alarm both ways on separate instances, 10 s out:

```
PLAIN:   set ctx.alarm=10; read back=10 type=number; getAlarm()=null
STORAGE: setAlarm(now+10s); getAlarm()=1790539735785 type=number in 10s
*** ALARM FIRED ***   (the setAlarm instance only)
```

The `ctx.alarm` arm read back `10` — exactly as production did — while
`getAlarm()` returned **`null`**: the runtime had no alarm. The `setAlarm` arm
returned a real timestamp and fired. This is the check that was never run.

### The fix

```js
const fireAt = Date.now() + ms;
const armed = this.ctx.storage.setAlarm(fireAt);
```

`setAlarm` returns a promise, and `scheduleAlarm()` is called from synchronous
contexts (constructor, `recordConnection`, the generation brackets), so the
promise is `.catch()`-ed rather than left to reject unobserved.

Both temporary instrumentation blocks are removed. `alarm()` now reads
`getAlarm()` first, so any future "the alarm fired but the work did not happen"
question is answerable from a log line.

### Regression tests

`cloudflare-worker/tests/liveness.test.mjs` pins both directions: that
`scheduleAlarm()` uses `storage.setAlarm(Date.now() + ms)`, and that **no**
executable line anywhere in the file assigns to `ctx.alarm`. Verified to fail
when the old line is reintroduced (mutation-checked, not just written green).

### Why it survived so long

It was introduced in `85a370b` (2026-09-27), which replaced a working
`setInterval` keepalive. Nothing was broken at that moment — the keepalive
simply stopped existing, and the symptom that got noticed first (connections
never reaped) had an innocent-looking explanation waiting for it. Before that
commit the bridge did not depend on alarms at all, so the defect had no
opportunity to appear.

## What is *not* proven — do not repeat these

Each of these was asserted from code-reading alone and each was wrong:

- **✗ "the alarm is skipped because `hasActiveWork` is false at the re-arm"**
  Plausible from reading `alarm()`, but nothing logged that branch. It was
  never reached, because `alarm()` never ran. *(It is a real latent path — see
  "Still worth knowing" below — but it was not this bug.)*
- **✗ "`ctx.alarm` is never set" — "disproved by the read-back above."** The
  disproof was circular: the read-back read the property the same function had
  just written. The real position is that the assignment meant nothing to the
  runtime. **The original claim was closer to right than its refutation.**
- **✗ "the MCP keepalive count proves the alarm is dead"** — **weak probe.**
  `alarm()` only writes keepalives when `mcpSessions` is non-empty. The
  measurement opened an SSE stream with GET and never POSTed on that session,
  so it may never have been registered. Do not use this as evidence. Send a
  POST on the session first.
  *(In the end this probe did point at a real dead alarm — it just could not
  distinguish "alarm dead" from "session never registered".)*

## Why this matters

The near-zero idle CPU currently measured (2 ms across 23 minutes) is a **side
effect of this bug**, not evidence of good tuning. Fixing the alarm will raise
idle CPU to roughly 360 CPU-ms/day (`docs/TUNING.md`) — that is correct
behaviour being restored, and still a rounding error against the ~1,000,000
ms/day free-tier budget.

Until it is fixed there is no liveness detection at all: a dead extension holds
its slot until something else evicts it.

## Still worth knowing

Two things that are *not* the bug, and are not yet fixed:

- **The skip-re-arm path is real.** If the constructor-armed alarm fires while
  nothing is connected, `alarm()` skips the re-arm and the alarm is unset until
  the next connection, generation, or deploy. `recordConnection()` arming on
  connect (KAN-168) closes the practical version of this, but a DO that goes
  idle and is then *not* reused still needs a new event to restart the cadence.
  That is the intended "stay evictable when idle" behaviour, not a defect.
- **Production has never run a real `alarm()` tick.** Everything measured to
  date was produced by a build whose alarm was a no-op, so no production
  observation about the keepalive cadence can be trusted as a baseline. The
  first post-fix deploy is the first genuine measurement of any of it.

The `scheduleAlarm(reason)` parameter **stays**. It was flagged as temporary

want to see when a keepalive misbehaves, and it costs nothing while
`BRIDGE_VERBOSE` is off. `alarm()` also reads `getAlarm()` on entry — kept
permanently, since it is the one check whose absence caused this whole episode.

The arm-on-connect call added in `3352474` is **not** diagnostic — it is
correct defensive code (a connecting client should re-arm the cadence) and can
stay.

## Tooling notes

**Reading a service worker's console** — a SW runs in its own execution
context, so its logs never appear in a page's DevTools console.

```bash
node scripts/sw-console.mjs <port> <ext-id-substring> <seconds>
```

Chrome must be started with `--remote-debugging-port`. The script header
documents two traps that cost two production incidents:

1. Chrome 137+ ignores `--load-extension`, so a throwaway profile cannot be
   seeded with the extension from the command line.
2. Never run a second profile against a live production DO. Both extensions
   hold the same slot; the second is 409'd forever. That presents as a client
   that connects, gets evicted, and cannot recover — which reads as a reconnect
   bug and sends you into the extension instead of the server.

**`BRIDGE_VERBOSE=1`** (`wrangler deploy --var BRIDGE_VERBOSE:1`) un-gates
`vlog()`. **Turn it off when finished** — it re-enables 23 hot log sites and
costs real CPU. Prefer a targeted `console.warn` for one-off diagnostics.

`45765a55-d652-421c-8096-940cebfd0bf7`, project `KAN`. Credentials in `.env`
(gitignored): `JIRA_BASE_URL`, `JIRA_EMAIL`, `JIRA_GEMINI_PASS_API_TOKEN`. Use
Basic auth with `JIRA_EMAIL`. The GitHub-side `JIRA_CI_TOKEN` secret and

## A note on process

Four production deploys went into this bug, and the first three were spent
confirming things that a single `wrangler dev` run would have shown. The
mistake was treating production as the place to test a hypothesis. When the
next question is "does X work at all in this environment", build the smallest
thing that answers it and run that first — the production DO is currently
without liveness detection, and every deploy to it is a real cost.
